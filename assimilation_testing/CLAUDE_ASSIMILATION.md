## Project Context for Claude

### Sub-Project Summary

The Assimilation Testing sub-project pulls real WSPR spot data from [wspr.rocks](https://wspr.rocks) and compares it against BCR/SNR/PR predictions generated by the main dashboard's ITU-R HF propagation engine. The goal is to empirically validate prediction accuracy using live ionospheric observations from the global WSPR network.

**Key distinction from the main dashboard**: This sub-project **requires internet access** to query wspr.rocks. The offline-first constraint that governs the main dashboard does NOT apply here.

### Key Technical Details

- **External Data Source**: [wspr.rocks](https://wspr.rocks) — public WSPR spot archive since 2008
- **Database Engine**: ClickHouse (hosted at wspr.live)
- **Primary Table**: `wspr.rx`
- **Spot Volume**: ~9,500+ spots per 2-minute cycle for 6 HF contest bands; wspr.rocks UI caps at 5,000 rows but the direct wspr.live API is uncapped
- **Time Column**: `DateTime` type (not Unix integer) — use `time >= now() - INTERVAL N MINUTE` for comparisons
- **Columns**: `id, time, band, rx_sign, rx_lat, rx_lon, rx_loc, tx_sign, tx_lat, tx_lon, tx_loc, distance, azimuth, rx_azimuth, frequency, power, snr, drift, version, code`
- **Prediction Engine**: `prediction/bcr_prediction.py` in the parent project

### Canonical Fetch Query (single WSPR cycle, 6 HF contest bands)

```sql
SELECT
    id, time, band,
    rx_sign, rx_lat, rx_lon, rx_loc,
    tx_sign, tx_lat, tx_lon, tx_loc,
    distance, azimuth, rx_azimuth,
    frequency, power, snr, drift,
    version, code
FROM wspr.rx
WHERE time = toStartOfInterval(now() - INTERVAL 5 MINUTE, INTERVAL 2 MINUTE)
  AND band IN (1, 3, 7, 14, 21, 28)
ORDER BY band ASC
FORMAT JSONEachRow
```

Used via `http://db1.wspr.live/?query=<URL-encoded SQL>`. See `fetch_spots.py` for the Python implementation.

### Related Components

- **Main prediction engine**: `prediction/bcr_prediction.py`
- **CCIR ionospheric data**: `prediction/data/ccir_coefficients.py`
- **Main project documentation**: `docs/CLAUDE.md`
- **wspr.rocks SQL Explorer**: https://wspr.rocks (requires internet)

**Key Decisions**:
- `WHERE time = toStartOfInterval(now() - INTERVAL 5 MINUTE, INTERVAL 2 MINUTE)` targets exactly one completed WSPR cycle, avoiding partial-cycle truncation
- `FORMAT JSONEachRow` on the direct API (one JSON object per line)
- TX bounds `tx_lat BETWEEN 36.5 AND 46.5`, `tx_lon BETWEEN -77.5 AND -72.5` — box kept tight to preserve path-specific validation accuracy
- ITURHFProp called directly in server.py (not proxied to main dashboard) — fully standalone
- `Path.BW` and `Path.SNRr` must be floats (`2500.0`, `-29.0`); integer format triggers error 113
- ITU-R P.533 is undefined below 2 MHz; 160m (1.8366 MHz) is an unsupported band — no proxy applied, acknowledged as a known limitation
- `Path.txpower` minimum is −30.0 dBkW (1 W = 30 dBm); standard WSPR 200 mW (23 dBm) is below this floor and causes error 113 — predictions run at ≥1 W
- `Path.hour 1,2,3,...,24` (all 24 hours, comma-separated) required for area mode; single-integer format causes error 113
- UTC hour derived via `statistics.mode()` across all spots' timestamps; `h = max(utc_hour − 1, 0)` used as 0-indexed slice into the 24-hour result array
- Leaflet custom panes (basemap z=200, heatmap z=300) required because GeoJSON async load would otherwise cover heatmap rectangles
- Canvas overlay placed at `mapPred.getBounds()` but pixels outside `[−180, 180]` longitude are transparent — prevents world-repeat without restricting the overlay bounds calculation
- On-demand per-band 1-hour fetch gives ~10× more spots than the previous 8-cycle all-band startup fetch, at no extra cost since only the selected band is queried

### Session 2: Bidirectional WSPR Fetch, PSK Reporter Removal, Ocean Masking, Log Scaling, Color Scale Unification
**Date**: May 1, 2026
**Time**: 11:30 AM – 12:45 PM and 3:00 PM – 6:00 PM (4.25 hours total)
**Model**: Claude Sonnet 4.6 (claude-sonnet-4-6)
**Contributor**: Liam Miller
**Scope**: Bidirectional WSPR fetch (TX+RX directions), PSK Reporter disabled, ocean masking on spot canvas, dynamic log-base spot scaling tied to total spot count, unified 10-chunk discrete viridis color scale on both maps

---

#### Block 1 (11:30 AM – 12:45 PM)

**Activities**:
- **Bidirectional WSPR fetch**: Redesigned `fetch_spots_for_band` in `server.py` to issue two ClickHouse queries per band instead of one:
  - **TX query**: `tx_lat/tx_lon BETWEEN` FN21 bounds — fetches spots where FN21 stations are transmitting; plots decoder (`rx_lat/rx_lon`) locations globally
  - **RX query**: `rx_lat/rx_lon BETWEEN` FN21 bounds — fetches spots where FN21 stations are receiving; for these rows `tx_lat/tx_lon` (the remote beacon) is swapped into `rx_lat/rx_lon` before being returned so `bin_spots_by_band` always bins by the non-FN21 end
  - Both query results concatenated into one list; spot files saved as `spots_YYYYMMDD_HHMM_<band>_tx.json/csv` and `spots_YYYYMMDD_HHMM_<band>_rx.json/csv`
  - Net effect: ~2× spot density on the spot map, now showing full bidirectional propagation paths through FN21
- **PSK Reporter disabled**: PSK Reporter returns one aggregated record per unique (TX, RX) pair — over 65 minutes on 20m this yields only ~400 unique circuits vs WSPR's 16k raw decodes. Extending the window would misalign PSK data with the ITURHFProp UTC-hour prediction, so PSK was removed:
  - `server.py`: `xml.etree.ElementTree` import commented out; `BAND_PSK_FRANGES` and `PSK_API` constants commented out; three PSK functions (`maidenhead_to_latlon`, `_fetch_psk_raw`, `fetch_psk_spots_for_band`) wrapped in `if False:` block to preserve code; PSK fetch block and response fields in `api_compute` commented out
  - `heatmap_viewer.html`: PSK state fields commented out; `mergedSpotGrids()` simplified to `return state.spotGridsByBand` with old merge logic preserved in `/* */` comment block; PSK state assignments in compute handler commented out; status message and CSV params simplified to WSPR-only

---

#### Block 2 (3:00 PM – 6:00 PM)

**Activities**:
- **Ocean masking on spot canvas**: Added per-pixel `LAND_MASK_PX` check to `renderSpotCanvasLayer` — identical to the existing check in `renderPredCanvas`. `valGrid` is written before the check (so marching-squares contours see no discontinuity at coastlines); ocean pixels then skip painting via `continue`. Uses the same 2880×1440 single-channel mask built once in `initBasemaps()`.
- **Dynamic log-base spot scaling**: Changed BCR spot normalisation denominator from `ln(meta.bcr_max)` (log of densest cell) to `ln(state.spotCount)` (log of total spots for the band). This makes the log base `b = spot_count^(1/10)`, so `log_b(spot_count) = 10` by construction — the legend maximum is always a clean "10" regardless of data volume. Cells that are dense relative to the full dataset score high; the scale is consistent across compute runs. Legend `fmtMax` changed from `v => Math.log(...).toFixed(1)` to `() => '10'`; legend title updated from `'ln of Spots'` to `'Spot density (log scale)'`.
- **Unified 10-chunk discrete viridis scale**: Both prediction and spot renderers previously used `BCR_COLOR_LUT` — a 1001-entry sigmoid S-curve LUT designed for raw BCR percentages, which produced visually inconsistent colors when fed log-normalised spot density values. Replaced both color lookups with `VIRIDIS[Math.min(9, Math.floor(norm / 10))]` — direct indexing into the 11-stop viridis table, giving exactly 10 equal-width discrete color bands (0–9 → darkest purple, 90–100 → bright yellow) on both maps. `BCR_COLOR_LUT` is now dead code (retained but unused).

---

**Key Decisions**:
- The "remote end" coordinate invariant: `rx_lat/rx_lon` passed to `bin_spots_by_band` must always hold the station **outside** FN21; for RX-in-FN21 spots the `tx_lat/tx_lon` swap is done in the Python fetch layer, not in the JS renderer
- PSK Reporter `if False:` pattern (not deleted) keeps the full implementation parseable by Python while ensuring it never executes — preserves context for a future revival if a per-decode FT8 data source is found
- `LAND_MASK_PX` is shared between both canvases; no second GeoJSON load needed
- `state.spotCount` (set from `result.spot_count` after every `/api/compute`) is used directly in `renderSpotCanvasLayer` — consistent with the existing pattern of referencing `state` in that closure
- 10-chunk discrete viridis was chosen over continuous interpolation to match the 10-tick legend visual and make color boundaries legible at a glance

- **Spot legend log-base title**: `updateLegends()` now dynamically sets the spot legend title to `log<sub>B</sub>` where B is `spot_count^(1/10)` formatted to 3 decimal places; falls back to the static param title when no spot count is available
- **Opacity dropdown**: Added `#opacity-bar` div (between status bar and maps) with a `<select>` offering 0.0–1.0 in 0.1 steps, default 0.8. Purely client-side — `change` event calls `predOverlay.setOpacity()` and `spotOverlayHolder.overlay.setOpacity()` without triggering a recompute. `getOpacity()` helper reads the value and is called when overlays are first created after each Compute.
- **Spot file cleanup fix** (`server.py`): `cleanup_old_spots()` was silently failing on bidirectional filenames (`spots_YYYYMMDD_HHMM_<band>_tx.json`) because `datetime.strptime(stem, 'spots_%Y%m%d_%H%M')` requires an exact full-string match. Fixed with `re.match(r'spots_(\d{8}_\d{4})', stem)` to extract just the timestamp prefix. Also moved the `cleanup_old_spots()` call to the top of `api_compute` so cleanup runs on every compute, not only at server startup.
- **Viridis top-chunk fix** (`heatmap_viewer.html`): Both canvas renderers used `VIRIDIS[Math.min(9, Math.floor(norm / 10))]`, capping the index at 9 (`[188,223,42]`, chartreuse). Changed to `VIRIDIS[Math.min(10, Math.floor(norm / 10) + 1)]` so norm 90–100 maps to `VIRIDIS[10]` (`[253,231,37]`, true yellow). The `+1` shift means `VIRIDIS[0]` is skipped for painted pixels since `paintThreshold=10` keeps norm 0–9 transparent.
- **PSK Reporter spot file deletion**: All 18 stale PSK Reporter files (`psk_reporter_*.json/csv`) manually deleted from `assimilation_testing/Spot Files/`.

---

**Key Decisions**:
- Opacity is a display-only concern — it does not affect prediction or spot data, so it must not trigger a recompute. Placed in its own `#opacity-bar` outside `#controls` to make this visually clear to the user.
- `re.match` timestamp extraction in `cleanup_old_spots()` is intentionally lenient — any future filename variant that starts with `spots_YYYYMMDD_HHMM` will be handled without code changes.
- `+1` in viridis indexing means the effective visible painted range is `VIRIDIS[2]`–`VIRIDIS[10]`; `VIRIDIS[1]` is only reachable for norm 0–9 which is below `paintThreshold` and never rendered.

## Technical Constraints to Remember

### CRITICAL: Internet Required

**This sub-project requires active internet access to query wspr.rocks / wspr.live.**

This is the opposite of the main dashboard's offline-first constraint. Code in `assimilation_testing/` may make outbound HTTP requests to `wspr.live` and should not be integrated into the offline-capable main dashboard without an explicit offline data caching layer.

### Isolation Boundary

All code and data files for this sub-project live under `assimilation_testing/`. Do not import from or modify the main `app/`, `static/`, or `templates/` directories.

### wspr.rocks Hard Limits

- **5,000 row maximum** per query — always include `LIMIT 5000`
- **All 20 columns required** for wspr.rocks to render results (direct wspr.live API is more flexible)
- **ClickHouse SQL only** — MySQL or PostgreSQL syntax may not work
